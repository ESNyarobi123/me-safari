# Database, infrastructure and recovery

The authoritative database is PostgreSQL 17.11. Prisma 7.10 generates its ESM client into `packages/database/src/generated/prisma`; `@ma/database` exports `createDatabase()`, `PrismaClient` and `Prisma`. The pool defaults to ten connections with five-second connect, ten-second statement and fifteen-second query limits. Transactions have bounded waits and timeouts.

## Safe local startup

Run from the repository root with the project's Node 24 runtime and pinned pnpm:

```sh
pnpm setup:local
pnpm infra:up
pnpm db:generate
pnpm db:migrate
pnpm db:seed
pnpm dev:api
# In another terminal:
pnpm dev:worker
```

`infra:up` starts Compose with health checks and runs `scripts/init-infra.mjs`, which creates `ma_safaris_test` only if missing. Neither startup nor seeding resets data. `docker compose down` retains named volumes; `down --volumes`, `prisma migrate reset`, and database truncation are intentionally absent from ordinary startup.

Use the `.env` generated by setup. Database credentials, JWT secrets, webhook secrets and the development account password are local-only. The main database is `ma_safaris`; the independent integration database is `ma_safaris_test`. Port 5433 publishes PostgreSQL, 6380 Redis, 1025 SMTP, and 8025 the Mailpit inbox. All are bound to loopback. For device testing, the API binds to the LAN while database/Redis remain private.

The database package's Prisma config explicitly loads root environment settings. CLI schema operations use an environment connection; they do not embed URLs in the schema. Deployment applies committed migrations with `prisma migrate deploy`, then explicitly generates the client. Prisma 7 does not implicitly seed or generate in these commands.

## Schema and integrity

There are 62 relational entity models covering identity, grants, sessions, customer/staff profiles, catalog/pricing, inquiries/custom requests, quote versions, bookings/travelers/pickup, itineraries, trips/resources, ledger/refunds, documents, support, notifications, outbox, idempotency and reports. IDs are UUIDs; display references are unique identifiers unrelated to authorization. Core relationships use restrictive foreign keys. Money is PostgreSQL bigint in explicit ISO currency minor units; API serialization returns decimal strings.

Four committed migrations install the relational schema, advanced invariants, paid-seat retention and published-history safeguards. The additional SQL includes:

- Half-open GiST exclusion intervals prevent two active allocations for one guide/vehicle. A trigger resolves resource foreign keys and checks guide grants/status/leave and vehicle status/capacity. Concurrent staff blocks and assignments lock the same staff row.
- A locked departure capacity check counts valid HELD, PAID and CONFIRMED reservations. PAID keeps capacity during staff review; expired unpaid holds are released explicitly.
- Captures, refund postings, financial adjustments, audit, trip events, handovers, policies, price versions and company setting versions reject updates/deletes. Accepted booking financial snapshots and sent quote contents remain immutable.
- Capture currency/amount/origin match the intent or verified offline evidence. Provider references/events are unique. Refund reservations lock their capture and cannot exceed it; settlement requires matching approval.
- One booking per accepted quote, one trip per booking, one current trip assignment, one sent/accepted quote per request, one published itinerary per owner, one active user role, one lead traveler, one open change request, and one pending payment intent use unique or partial indexes.
- Counts, dates, line-item math, amounts, child pricing bands, policy basis points, star ratings and supported status values have database checks. The last active Admin is protected even against a direct database update.

Database safeguards complement application authorization and version checks. They do not replace role, ownership, field projections or business transition enforcement. Lead/customer travel details are completed before Operations confirmation. Financial mutations append adjustments or postings; they never rewrite old captures. Advanced SQL constraints are preserved as committed migration sources, rather than regenerated away by `db push`.

Development uses the isolated Compose owner account. Production should separate a migration/extension owner from an application role, grant only required table/sequence access, prohibit history UPDATE/DELETE, restrict schema ownership, and retain a privileged audited operator role for approved retention/restoration. A superuser can disable triggers, so production must not run ordinary API requests as a database superuser.

## Development fixture

Seeding is development-only and rejects missing/placeholder passwords. It obtains `SEED_DEMO_PASSWORD` from the local environment and hashes each newly created account with Argon2id and a random salt. Running seed again preserves existing account passwords, business records and dates. Demo contact information, policy, prices and assets are explicitly examples.

Main accounts are `customer.demo@ma-safaris.local` (Alice), `operations.demo@ma-safaris.local` (Neema), `guide.demo@ma-safaris.local` (Kelvin), and `admin.demo@ma-safaris.local`. `customer2.demo@ma-safaris.local` and `guide2.demo@ma-safaris.local` exist for denial checks. The shared local password is recorded in the ignored `var/demo-accounts.txt` generated by setup, never in committed documentation.

The first seed creates a dynamically dated connected confirmed/prepared Serengeti fixture for Alice and Daniel, Kelvin and TZ001, with an immutable full mock capture and queued receipt/itinerary events. All roles inspect the same IDs. The fixture is persisted rather than silently moved or reset on subsequent seed runs.

## Worker recovery and reconciliation

Business transactions insert unique outbox events in PostgreSQL. BullMQ transports work, while PostgreSQL remains the recovery record. The worker polls pending/failed/stale-dispatched events, uses stable queue IDs and a per-event PostgreSQL advisory lock, and commits DONE only after idempotent documents/notifications and delivery handling. Logical document/notification/delivery keys prevent ordinary retries from duplicating durable artifacts.

PDF files and CSV exports are stored with random document IDs in private storage using atomic file rename, checksums, restricted file permissions, and no public directory mount. Receipt documents link settled capture IDs; quotations link sent versions; itineraries link published versions. Customer PDFs omit supplier costs, guide notes and internal deliberations. CSV text beginning with formula prefixes is escaped. Download authorization is checked by the API even for already-ready artifacts.

Every thirty seconds the worker queries the mock adapter's known status before expiring holds. UNKNOWN/PROCESSING reservations remain for reconciliation. Only a known-empty expired mock PENDING intent releases its payment reservation. A genuine late capture is still posted and produces a visible finance/capacity exception. Live-provider reconciliation remains disabled until an actual provider adapter is configured.

Emails are sent to Mailpit through SMTP with stable message IDs. Authentication email payloads are encrypted in the outbox; transaction notification templates are constructed from scoped records. Accepted SMTP state is separate from eventual delivery. A crash leaving a SENDING record is ambiguous and requires operator review, because SMTP does not supply exactly-once delivery. To recover, inspect Mailpit/provider evidence, preserve accepted delivery when found, or mark a known-undelivered attempt FAILED before an authorized job retry. Failed document/export/outbox jobs remain visible and can be retried through the allowed Admin API.

## Backup and restore

```sh
pnpm backup:local
# Or choose a destination:
node scripts/backup-local.mjs var/backups/my-check
node scripts/restore-local.mjs var/backups/my-check ma_safaris_restore_my_check
```

The backup uses the container's PostgreSQL 17 `pg_dump` in custom format and archives private files. A manifest records SHA-256 checksums and byte counts. Backups contain private information and must remain private. Store a separately protected copy of required server secrets, including the encryption secret needed to decrypt pending authentication-email events; the backup tool never prints or copies secret values.

For a consistent operational backup, pause business writes and stop the worker while copying database plus private files, or use a coordinated storage/database snapshot. Ordinary online development backups can race a document being generated and require reconciliation afterward. Production schedules, offsite encryption and retention are operator settings.

Restore validates checksums and only creates a new `ma_safaris_restore_*` database plus a separate restored file directory. It refuses to overwrite active databases. The command restores foreign keys, triggers and immutable history, then counts bookings/captures/audit rows. After verification, intentionally stop API/worker, point `DATABASE_URL` and `LOCAL_PRIVATE_STORAGE_PATH` at restored targets, restart, and recheck downloads/outbox/provider reconciliation. Never replay a provider capture without its durable uniqueness checks.

Worker generated and visually verified real receipt/itinerary PDFs. Detailed API, concurrency, mobile and web acceptance evidence is maintained in the verification report.
